    CLI Command Reference¶

    The CLI provides direct, text-based access to the controller, available from the CLI tab in the Configurator, or over any serial terminal at the configured baud rate.

    Common commands¶

    Command Description
    help List available commands
    status Show system status
    version Show firmware version info
    dump Print the full configuration (including defaults)
    dump all Print the full configuration for all profiles
    diff Print only settings that differ from defaults
    diff all Print changed settings across all profiles
    save Save changes and reboot
    exit Exit the CLI (without saving)
    defaults Reset to firmware defaults

    Backup and restore¶

    diff all is the preferred backup format for day-to-day use -- compact, and easy to review. Paste the saved output back into the CLI and run save to restore it. See Backup & Restore for the full workflow.

    Serial port diagnostics¶

    serialdebug helps when a device on a serial port (GPS, receiver, telemetry, ESC sensor) isn't working. It shows how each port is set up, what the function on a port reports, and the raw data a port receives.

    Command Description
    serialdebug Show every port
    serialdebug <port> One port in detail, with what its function reports
    serialdebug monitor <port> [<baud>] [<seconds>] [inverted] Print what a port receives
    serialdebug scan <port> [inverted] Try common baud rates and look for known protocols

    <port> is the port number used by the serial command (UART1 is 0, UART7 is 6, UART10 is 9) or its name, such as UART7. serialdebug with no arguments lists the numbers, and serialdebug help prints the usage.

    All ports¶

    # serialdebug
port     id  rx   tx   functions         open  baud
VCP      20  -    -    MSP               yes
UART1     0  -    -    -                 no pins
...
UART3     2  D09  D08  RX_SERIAL         yes   460800 (irq rx)
UART7     6  E07  E08  GPS               yes   57600
UART10    9  E02  E03  -                 no
...
    • rx / tx: the pins assigned with resource SERIAL_RX / SERIAL_TX.
    • open: whether the port is running. NO (in capitals) means it has a function but did not open. no pins means no pins are assigned, so the port can't be used. PIN CONFLICT means one of its pins is also used by something else, such as a servo or LED; see resource show.
    • (irq rx): the port's owner reads incoming bytes as they arrive (for example a serial receiver); monitor still works on it.

    Lines starting with # point out setup problems: a port whose function did not open, a pin conflict, or a gps_provider with no matching port (for example UBLOX with no port set to GPS, so GPS is off).

    One port¶

    serialdebug 6 shows UART7 in detail: its pins and functions, the baud rates configured for each function type, and if it is open, the live baud rate, direction, inversion, half duplex and how many bytes are waiting to be read. Then each function on the port that can report its state adds a block. GPS reports:

    GPS: provider UBLOX, active yes
GPS: state RECEIVING_DATA, last valid message 85ms ago, at 57600 baud
GPS: bytes 91230, packets 1520, errors 0, timeouts 0, sats 11, fix yes
    • active: whether GPS was started at the last boot. GPS starts only when gps_provider matches a port (see the GPS tab). setup changed: save and reboot means the port or provider changed since the last boot.
    • state: INITIALIZING or LOST_COMMUNICATION means no valid messages are arriving. RECEIVING_DATA means the module is talking.
    • bytes / packets / errors / timeouts: everything received, valid messages, bad messages (wrong checksum, usually noise or a wrong baud rate) and times the module went silent.

    The hints tell the cases apart: no bytes at all points at wiring or power, bytes without packets at the baud rate or protocol, and GPS set on more than one port means only the first one is used.

    Watching a port¶

    serialdebug monitor 6 prints what UART7 receives for 5 seconds. Readable text is shown as is, other bytes as <hex>. A working NMEA GPS shows lines like $GNGGA,..., a u-blox in binary mode shows <B5>b..., a CRSF receiver shows <C8><18><16>.... If nothing arrives, check that the device's TX goes to the controller's RX pin, and check power and ground.

    The baud rate defaults to the port's current rate (or its GPS baud rate if the port is closed). Give one to try another, for example serialdebug monitor 6 9600 10 listens at 9600 baud for 10 seconds (up to 60). Add inverted for a signal that is inverted, such as S.Bus; a port that is already open keeps its own setting.

    Finding the baud rate and protocol¶

    serialdebug scan 6 listens for 1.5 seconds at each of 9600, 19200, 38400, 57600, 100000, 115200, 230400, 400000, 416666, 420000 and 460800 baud, and counts the NMEA, UBX, CRSF and FBUS frames it recognises at each:

       9600:   960 bytes, 100% text, 16 NMEA
  19200:   480 bytes,  41% text
...
# looks like NMEA at 9600 baud

    Set the port's baud rate (or for GPS, turn on gps_auto_baud) to match. S.Bus is not recognised; use monitor with inverted for it.

    Note

    While monitor or scan runs the controller does nothing else, so only use them on the bench. Press any key to stop early. A port already in use (such as the GPS port) is borrowed and set back afterwards.

    Settings¶

    set <name> = <value> changes a setting, get <name> shows its value and allowed range (get with part of a name lists every setting that matches), and save stores the changes and reboots.

    The tables below list every setting in the firmware, grouped by topic.

    • Scope: global settings apply whatever profile is active. PID profile settings belong to the PID profile selected with profile <n> (0-5), rate profile settings to the one selected with rateprofile <n> (0-5): select the profile first, then set. diff all and dump all list every profile. global (hw) settings describe the board (buses, sensor orientation, pins); they normally come from the board configuration and are listed by dump hardware.
    • Default: the value on a unified target before a board configuration (gripora-targets) is applied. A board configuration can change it, and board means the value depends on the board. defaults in the CLI resets to the board's own defaults.
    • Some settings only exist when the firmware includes the feature (LED strip, SD card, a built-in SPI receiver, the F.Bus mux FPGA, a particular MCU), so get on a given board may not list all of them.

    Gripora stabilises only the steering (the yaw axis). Roll and pitch keep their settings in the PID and rate profiles so backups and MSP keep their layout, but they hold zero and have no effect on a car.

    Removed settings¶

    These WingFlight settings went with the aircraft features (angle and leveling, acro trainer, attitude hold, GPS rescue and navigation, thrust vectoring, the governor, cross-axis, snap and prop-hang relax):

    • governor_*, gps_rescue_*, nav_*, tv_*, angle_*, acro_trainer_*, atthold_*, cross_axis_relax_*, snap_relax_*, prop_hang_* and failsafe_stick_threshold
    • the tv_profile command

    Pasting a diff from WingFlight or older Gripora reports these lines as unknown; they can be ignored. Settings whose range or defaults changed for a car (for example model_type, map, fw_spa_speed_max, the throttle and failsafe defaults) were reset to the new defaults when the firmware was upgraded, so check them after restoring an old backup.

    Debug modes¶

    debug_mode picks what the Blackbox debug fields record. Gripora's own modes:

    DRIVE shows the drive state:

    Field Value
    0 Throttle command, x1000
    1 Commanded ESC state: 0 neutral, 1 forward, 2 brake, 3 reverse
    2 Travel direction (+1 forward, -1 reverse)
    3 Speed, 0.1 km/h
    4 Speed known (1 = there is an RPM source)
    5 Gyro correction scale, x1000
    6 Motor 1 RPM
    7 Stopped (1 = RPM shows the car stopped)

    DRIVE_AIDS shows the drive aids:

    Field Value
    0 Throttle from the transmitter, x1000 (below 0 is brake/reverse)
    1 Throttle to the ESC, x1000
    2 Flags: bit 0 aids on, bit 1 ABS armed, bit 2 ABS releasing, bit 3 traction control armed, bit 4 traction control holding the throttle back, bit 5 launch staged, bit 6 launching
    3 While braking with ABS: pulse rate, x10 Hz. While driving forward with traction control or launching: the throttle allowed, x1000
    4 ABS release brake (floor), x1000
    5 ABS hold, ms
    6 Time into the current ABS pulse, ms
    7 Steering, x1000

    GAIN_ATTEN shows the throttle (TPA) and speed (SPA) gain attenuation that scales P, D, F and B:

    Field Value
    0 Throttle attenuation, x1000 (1000 = 100%)
    1 Speed attenuation, x1000
    2 Speed used by the curve, 0.1 km/h (motor RPM wheel speed, else GPS)
    3 Raw GPS speed, cm/s
    4 GPS fix (1 = fix)

    ALTITUDE shows the altitude estimate next to its sources:

    Field Value
    0 Altitude, cm (what telemetry uses)
    1 Vario, cm/s
    2 Measured altitude before fusion, cm
    3 Measured vario (derivative of the measured altitude), cm/s
    4 Barometer altitude, cm
    5 GPS altitude, cm

    7 Learned accelerometer error, cm/s²

    Servos¶

    There are 24 servos. Servo N is sent on PWM output N, where the board has one, and on bus channel N (see fbus_master_channels and sbus_out_channels above, and the Servos tab; channels past the count are sent at centre). The servo command lists the servos in use and sets one:

    servo <index> <mid> <min> <max> <rneg> <rpos> <speed> <flags>
    Argument Range Default Meaning
    <index> 1 to 24 The servo
    <mid> 1000 to 2000 1500 Center, µs
    <min> -1000 to 0 -600 Lower travel limit, µs from center
    <max> 0 to 1000 600 Upper travel limit, µs from center
    <rneg>, <rpos> 50 to 1000 500 Scale on the negative and positive side, µs
    <speed> 0 to 60000 0 Speed limit, ms per 60°; 0 is no limit
    <flags> 0 Bit 0 reverse, bit 1 geometry correction

    The signal sent to a servo stays within 880-2159 µs. servo status, servo override, servo trim and servo name use the same index.

    servo name lists the servos that have a name, servo name <index> <name> sets one and servo name <index> clears it. A name is up to 8 printable characters and may contain spaces:

    servo name 1 STEER
servo name 2 REAR STR

    Names are labels only; nothing reads them while driving. diff and dump include them.

    Backups from before MSP API 22.16

    The servo line had a ninth value, a rate per servo, between <rpos> and <speed>. Such a line is still accepted and its rate is ignored. bus_servo_clone_pwm no longer exists. A servo, servo trim or mixer rule line that names servo 9 or above meant a bus channel 8 lower than it does now, so don't paste those lines back as they are.

    Mixer rules¶

    mixer rule <index> <operator> <input> <output> <weight> <offset> <weight-neg> <speed> <curve> <condition> <role>

    Everything after <offset> is optional: <weight-neg> defaults to the symmetric value, and the rest default to off. <operator> is set, add or mul; mixer rule <index> del deletes a rule and mixer rule reset goes back to the default rules. dump and diff print rules in this form, with names for the input and output. The default rules are the car preset (see Car Mixer, Channels and Gyro Direction):

    mixer rule 0 set SY S1 1000 0 1000 0 0 0 0
mixer rule 1 set ST M1 1000 0 1000 0 0 0 0

    Stabilized steering (SY) drives servo 1 and stabilized throttle (ST) drives motor 1. The drive aids work on the stabilized throttle, so an ESC rule fed from the RC throttle (CT or RT) bypasses them.

    <output> is a number or a name:

    Output Name Meaning
    0 - None
    1-24 S1-S24 Servos 1-24
    25-26 R25, R26 Reserved
    27-30 M1-M4 Motors 1-4

    <input> is a number or a name:

    Input Name Meaning
    0 None
    1-4 SR, SP, SY, ST Stabilized roll, pitch, steering, throttle. Roll and pitch are always zero
    5-8 CR, CP, CY, CT RC command (stick deflection after the deadband) roll, pitch, steering, throttle
    9-12 RR, RP, RY, RT RC channel roll, pitch, steering, throttle
    13-26 AUX1-AUX3, CH8-CH18 RC channels 5-18
    27-29 TR, TP, TY Reserved (thrust vectoring removed), always zero
    30-35 CH19-CH24 RC channels 19-24

    RC channels here are in the firmware's own order (roll, pitch, steering, throttle, then AUX), after the map command has been applied, not the order on the receiver. With the default car map RT1234AE, CH1 is steering, CH2 throttle, CH3-CH6 AUX1-AUX4 and CH7/CH8 roll and pitch.

    The optional last argument, <role>, is a label for the Configurator: 0 none (the default when omitted), 1 Flap Compensation, 2 Differential Thrust Yaw. Both named roles are inherited from WingFlight; the mixer never reads the role. See Mixer.
